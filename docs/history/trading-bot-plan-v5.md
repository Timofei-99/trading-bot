# Торговый бот на основе ICT Smart Money

> Документ-план для разработки автоматизированного торгового бота на основе визуального анализа графиков по концепциям ICT (Inner Circle Trader) / Smart Money.
>
> **Статус:** черновик, в активной разработке
> **Последнее обновление:** 2026-05-29

---

## 1. Контекст и цель

**Цель проекта:** построить **конструктор торговых стратегий** на основе ICT Smart Money, который позволяет:

- Иметь библиотеку готовых ICT-инструментов (детекторов паттернов)
- Применять каждый инструмент на любом таймфрейме
- Свободно комбинировать инструменты между собой и между ТФ
- Быстро тестировать любые комбинации на истории
- Без переписывания кода переходить от бэктеста к paper-торговле, а потом к live на реальном терминале

**Исходные данные:**
- Трейдинг ведётся визуально, без числовых индикаторов, только по чистому графику
- Используются концепции ICT Smart Money
- Есть наработанная интуиция и опыт, которые нужно формализовать

**Ключевая сложность:** перенос неявных, "интуитивных" правил принятия решений в однозначный код.

## 2. Архитектурный подход: конструктор стратегий

Это **главное архитектурное решение проекта**. От него зависит всё остальное.

Бот строится не как одна жёстко зашитая стратегия, а как **набор независимых компонентов с едиными интерфейсами**, из которых можно собирать любые стратегии.

### 2.1. Слои системы

1. **Данные** — `MarketContext`: хранит синхронизированные свечи по всем нужным таймфреймам
2. **Детекторы ICT** — независимые модули, каждый ищет один тип паттерна (ОБ, FVG, ликвидность, BOS/CHOCH и т.д.)
3. **Стратегии** — правила, комбинирующие детекторы в торговый сигнал
4. **Риск-менеджмент** — расчёт размера позиции, стопов, тейков
5. **Исполнение** — единый интерфейс `ExecutionAdapter` с разными реализациями (бэктест / paper / live)
6. **Движок** — связывает всё вместе: прогоняет данные через детекторы, передаёт в стратегию, исполняет сигналы

### 2.2. Единый интерфейс детекторов

Каждый ICT-инструмент — это класс с одинаковым контрактом:

```python
class Detector:
    def detect(self, candles: DataFrame) -> List[Pattern]:
        # возвращает список найденных паттернов
        # с координатами (время, цена) и метаданными
        ...
```

Все детекторы возвращают данные в **одном формате**, поэтому их можно комбинировать как угодно.

### 2.3. Мульти-таймфрейм через MarketContext

```python
context = MarketContext(symbol="BTCUSDT", timeframes=["1m", "15m", "1h", "4h", "1d"])
context.update(new_candle)

fvgs_15m = FVGDetector().detect(context.candles("15m"))
obs_4h = OrderBlockDetector().detect(context.candles("4h"))
```

`MarketContext` решает проблему синхронизации данных между ТФ — критическую для ICT, где почти всегда контекст со старшего ТФ и точка входа с младшего.

### 2.4. Стратегия как сборка из детекторов

```python
class Strategy:
    def check_entry(self, context: MarketContext) -> Signal | None:
        htf_ob = OrderBlockDetector().detect(context.candles("4h"))
        if not in_discount_zone(context, htf_ob):
            return None
        
        ltf_fvg = FVGDetector().detect(context.candles("15m"))
        if not price_entered(context.last_price(), ltf_fvg):
            return None
        
        if not liquidity_taken_below(context, "1m"):
            return None
        
        return Signal(direction="long", entry=..., stop=..., target=...)
```

Стратегия — это **правила поверх детекторов**. Детекторы переиспользуются между стратегиями.

### 2.5. Единый интерфейс исполнения

```python
class ExecutionAdapter:
    def place_order(self, signal: Signal): ...
    def get_position(self, symbol): ...
    def close_position(self, symbol): ...
```

Реализации:
- `BacktestAdapter` — виртуальные сделки на исторических данных
- `PaperAdapter` — реальные данные, виртуальное исполнение
- `BinanceAdapter`, `BybitAdapter`, `MT5Adapter` — реальная торговля

**Стратегия не знает, через что она торгует.** Меняем адаптер — тот же код едет с бэктеста в live.

### 2.6. Конфигурация стратегии — в YAML

Цель — собирать новые стратегии **без написания кода**, только через конфиг:

```yaml
name: "OB_4h_with_FVG_15m"
version: "1.0"
context:
  htf:
    timeframe: "4h"
    detectors: [order_block, premium_discount]
  ltf:
    timeframe: "15m"
    detectors: [fvg, liquidity]
rules:
  entry: "htf_ob_in_discount AND price_in_ltf_fvg AND liquidity_taken"
risk:
  per_trade: 1%
  stop: "below_ob"
  target: "next_liquidity_level"
```

Это конечная цель архитектуры. На старте можно описывать стратегии кодом, постепенно вынося в конфиги.

## 3. Технологический стек

### Язык
- **Python** — окончательный выбор. Для конструкторного подхода с переиспользованием компонентов, мульти-ТФ анализом, бэктестом и быстрыми итерациями — лучший вариант. Экосистема для алготрейдинга на Python несравнимо богаче.

### Данные и исполнение
- **CCXT** — единый интерфейс к крипто-биржам (Binance, Bybit, OKX и др.)
- **MetaTrader5** (Python-пакет) — если торгуем форекс/индексы
- **WebSocket напрямую** — на будущее, когда понадобится низкая задержка

### Хранение данных
- **Старт:** Parquet-файлы через pandas
- **Развитие:** DuckDB или TimescaleDB при росте объёмов

### Анализ
- **pandas / numpy** — основа всего
- **pandas-ta** или **TA-Lib** — только для базовых вспомогательных индикаторов (ATR и т.п.)
- **Своя ICT-логика** — пишется с нуля, готовых хороших библиотек нет

### Бэктест
- **Свой движок** — для мульти-ТФ и событийной логики ICT готовые фреймворки подходят плохо. Движок небольшой, зато даёт полный контроль.
- На совсем раннем этапе можно использовать `backtesting.py` для проверки отдельных идей, но основным он не станет.

### Визуализация (критично!)
- **Plotly** — интерактивные свечные графики с разметкой детекторов
- **lightweight-charts** (Python-обёртка TradingView) — выглядит как TV, удобно сверять с глазом
- **Jupyter** — основной инструмент для итераций по разметке

### Прототипирование
- **Pine Script** на TradingView — для быстрой визуальной проверки разметки паттернов перед портированием в Python

### Запуск в проде
- **VPS** (DigitalOcean / Hetzner / Contabo) — $5–10/мес
- **Docker** — контейнеризация
- **systemd** или **supervisor** — автоперезапуск

### Мониторинг и уведомления
- **Telegram-бот** — уведомления о сделках, ошибках, статусе
- **Grafana + Prometheus** — на будущее, для дашбордов

**Главные принципы:**
- Каждый ICT-инструмент — изолированный модуль с единым интерфейсом
- Стратегии не дублируют логику детекторов, только комбинируют их
- Исполнение отделено от стратегии — меняется адаптер, не код
- Параметры в YAML, не в коде

## 5. Поддержка и развитие проекта

Эта часть определяет, доживёт ли бот до результатов. Правила, которые соблюдаем с первого дня:

1. **Git с первого коммита.** Каждое изменение — отдельный коммит с понятным сообщением.
2. **Параметры — в конфиг, не в код.** Все числа в YAML. Меняем параметр — не трогаем код.
3. **Журнал каждой сделки.** Время, инструмент, какие детекторы сработали, цена, стоп, тейк, результат. Это будущий датасет для анализа.
4. **Версионирование стратегий.** Каждая стратегия имеет имя и версию (`v1.0`, `v1.1`...). Каждая сделка пишется с указанием версии — для честного сравнения "до и после".
5. **Стандартный бэктест-отчёт.** После каждого изменения — прогон по фиксированному историческому периоду. Метрики: profit factor, max drawdown, win rate, Sharpe. Стало хуже — откатываемся.
6. **Paper trading перед live.** Минимум 2–4 недели на демо или в режиме "только логирование".
7. **Тесты на детекторы.** Это самая критичная часть кода. Берём конкретный кусок истории → известный ответ → автотест. Без этого рефакторинг сломает разметку незаметно.
8. **Разделение dev / prod.** Не править код на сервере, где бот торгует. Только: пишешь → тестируешь → деплоишь.
9. **Аварийный стоп.** Кнопка "выключить всё" + автостоп при превышении дневной просадки.
